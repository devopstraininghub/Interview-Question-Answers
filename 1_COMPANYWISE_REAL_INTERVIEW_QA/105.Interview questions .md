### 2. Tell me about the architecture of your last project before HRC. How many services were there, what tools were you using, and how was it scalable?

**Answer:**

The healthcare application had approximately 10 microservices, including authentication, user management, appointments, processing, and notifications.

Each service had its own deployment in Kubernetes, which allowed us to deploy and scale services independently.

We managed the source code in Git. For CI/CD, I used Jenkins. The pipelines checked out the code, built applications using Maven, ran unit tests, performed SonarQube code-quality analysis, scanned dependencies, and used Trivy for Docker image scanning.

Then I built Docker images and pushed them to Amazon ECR. We used Helm charts and Kubernetes manifests.

### 3. How was your Jenkins server authenticated with ECR?

**Answer:**

We used secure and short-lived credentials instead of storing permanent AWS access keys. I configured a Jenkins IAM role through the Jenkins agent. Depending on the environment, the role had only the required permissions, such as pushing Docker images to Amazon ECR, reading required artifacts, and deploying to the target EKS cluster.

### 4. Why were you not using access keys?

**Answer:**

I avoided permanent access keys because they create a long-term security risk. If someone exposes the keys through a Jenkinsfile, build logs, workspace backups, or agents, they can continue using them until someone detects and revokes them.

Instead, I used an IAM role for Jenkins, which provided temporary credentials automatically.

After joining **Upstream**, I was also strictly prohibited from using access keys and secret access keys because they could lead to hacking. I followed best practices and avoided using those keys.

### 5. If your application needs a username, password, and hostname, how can you pass this information to the application?

**Answer:**

I would not hardcode the RDS username or password in the source code, Dockerfile, Git repository, or Jenkinsfile.

I would store sensitive values, especially passwords, in AWS Secrets Manager or AWS Systems Manager. The application would access the secret using an IAM role with only the required permissions.

When running in EKS, I would use a Kubernetes service account mapped to an IAM role through IAM Roles for Service Accounts. The role would have permission to read only the specific secret.

I would also use the Secrets Store CSI Driver or External Secrets Controller to provide the secret as a mounted file or Kubernetes secret.

### 6. Are you going to use a file path?

**Answer:**

Yes, I can mount it as a file, but that is not the only option. I would choose the method based on application requirements.

With the Secrets Store CSI Driver, the pod mounts the value retrieved from AWS Secrets Manager into a file. The application reads the secret from that file, and the value does not appear in the deployment manifest.

If the application expects environment variables, I can synchronize the external secret into a Kubernetes secret. The application can then read values such as database username and password from those environment variables.

### 8. If you have four environments, how would you design the Helm chart?

**Answer:**

I would create one reusable Helm chart and keep all environment-specific values outside the templates.

The chart would contain templates for deployment, service, ingress, ConfigMap, service account, and external secret references.

I would maintain separate values files for each environment, such as development, staging, and production.

### 9. In Kubernetes, if your application is running and you are getting a 503 error, how are you going to debug it?

**Answer:**

When we get a 503 error in Kubernetes, I would first confirm the scope and check whether the issue affects all requests, one endpoint, or only the development namespace.

I would start with the application ingress status and check whether the pods are ready.

A common reason for a 503 error is that the service has no healthy endpoints. I would compare the service selector with the labels on the pods.

### 10. What else can be the reason apart from that?

**Answer:**

I would check pod readiness, service selectors, and endpoints. I would also verify the service port and target port.

The service must forward traffic to the port where the container is actually listening.

I would test the application directly from inside the pod and through the Kubernetes service.

### 11. How are you going to bypass the firewall and directly hit the application?

**Answer:**

I would first test the request in stages, starting from inside the application pod and moving outward.

I would test the application locally inside the pod using the `kubectl exec` command. If it fails, the issue could be inside the application container, port configuration, or dependency connection.

### 12. How are you going to check the endpoint?

**Answer:**

I would check the logs and the endpoints from the service. The output should contain the IP addresses and ports of the ready application pods. If the output is empty, the service is not selecting any ready pods.

I would also inspect the service.

### 13. How are you going to actually hit the endpoint?

**Answer:**

I would create a temporary debug pod in the same namespace and use the curl command to call the application through the service. This directly tests the endpoint instead of only checking the configuration.

### 14. How are you going to identify whether the 503 error is coming from the application, database, or another layer?

**Answer:**

I would check the ELK stack or the organization's logging platform to trace the failed request across all layers.

I would open Kibana and filter by the time range, namespace, application, HTTP status, endpoint, and correlation or trace ID.

I would also review the logs from the load balancer, ingress controller, application pods, database proxy, and database.

For example, I would search for the development namespace and status 503.

### 15. If the application logs do not show a clear database error, what will you do?

**Answer:**

I would not assume the database is the cause. I would verify the connection path from the application to the database and correlate the results across the observability tools.

I would also check the centralized logs for the application, ingress, and database proxy.

### 16. If the application logs show a database connection timeout, what will you check?

**Answer:**

I would first confirm the exact RDS endpoint and port configured for the application.

I would check the ConfigMap and secret references without exposing the passwords.

### 19. The application was working fine until 2 PM, but now it is 2:23 PM and you are getting a connection timeout. What will you check?

**Answer:**

I would treat this as a time-based incident and first compare what changed around 2 PM.

I would check deployment history, configuration changes, secret rotations, RDS events, security group and network changes, and scheduled jobs.

I would start with centralized logs and CloudWatch for the exact time window.

I would also check application connection timeouts, RDS events, database connections, CPU, storage, failover status, and network-related metrics.

I would verify the current RDS endpoint and port from the application since the PostgreSQL port was changed. I would confirm that the application is running on the new port and that the RDS security group allows traffic from the application security group.

Using the `aws rds describe-db-instances` command, I would describe the database instance.

From an approved debug pod in the same namespace, I would test DNS and TCP connectivity.

If the port is unreachable, I would check the RDS security group, application security group, route tables, network ACLs, firewall changes, and Kubernetes network policies.

If the port is reachable, I would check database authentication, secret rotation, connection pool exhaustion, maximum database connections, locks, and slow queries.

I would compare the current application configuration with the last known working configuration.

I would also check whether a scheduled deployment, secret rotation, certificate change, backup maintenance, or auto-scaling event occurred at 2 PM.

After identifying the change, I would restore the service through an approved rollback or configuration correction, validate a real database transaction, and document the root cause.
