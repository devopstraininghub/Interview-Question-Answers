**Q18. Why do we need a Terraform state file?**

**A:** The Terraform state file maintains the relationship between Terraform configuration and AWS resources. It stores resource IDs, attributes, dependencies, and metadata.

**Q19. Where do you store the Terraform state file?**

**A:** We use an S3 bucket for storing the state file and DynamoDB for state locking.

**Q20. What happens if the Terraform state file gets corrupted or is lost?**

**A:** We may lose the state information. I would stop Terraform changes immediately and prevent further changes until the issue is resolved.

**Q21. If the Terraform state file is lost, will the AWS infrastructure automatically be destroyed?**

**A:** No. Losing the Terraform state file does not automatically destroy AWS resources. We can plan again and reapply the changes.

**Q22. How would you destroy a particular EC2 instance using Terraform?**

**A:** I would identify the Terraform resource and use the resource address. I mentioned using `terraform plan -destroy` and then `terraform apply` to apply the changes.

**Q23. Where do you run Terraform commands, locally or in CI/CD? How does your local state file sync with the remote state?**

**A:** I configure Terraform locally with the same remote backend. The CI/CD pipeline also uses the configured remote backend stored in S3, with DynamoDB for locking.

**Q24. Is it safe to configure the remote backend locally and apply changes?**

**A:** It is technically possible, but I would not allow restricted local access. We store the state in S3 and use DynamoDB for locking.

**Q25. How does Terraform identify which EC2 instance needs to be destroyed?**

**A:** Terraform identifies resources through their resource addresses and configuration. The instance ID is stored in the state file, which helps identify the resource.

**Q26. What does `terraform plan` do?**

**A:** It previews what changes are going to be applied. It shows whether resources need to be created, updated, replaced, or destroyed. It does not create or modify resources.

**Q27. What is a provider in Terraform?**

**A:** A provider is a Terraform plugin that communicates with a specific platform, such as AWS.

**Q28. What is the difference between a resource and a data source in Terraform?**

**A:** Resources create and manage infrastructure objects. Terraform stores them in the state file and can create, update, or destroy them.

Data sources read information about existing resources.

**Q29. What is a Terraform backend?**

**A:** A Terraform backend determines where the state is stored and how Terraform accesses it. It maintains the mapping between Terraform resources and infrastructure, such as instance IDs and VPC IDs.

**Q30. What is a Terraform module? Have you worked with modules?**

**A:** A Terraform module is a reusable collection of Terraform configuration files. It can contain resources, variables, outputs, and data sources. I also mentioned root modules and child modules.

**Q31. What are the lifecycle rules in Terraform?**

**A:** The main lifecycle arguments are:

- Create before destroy
- Prevent destroy
- Ignore changes

I also mentioned planning, validating the plan, and applying the changes.

**A:** It is a Terraform dependency lock file that is created or updated when Terraform runs. It maintains provider dependency information.
