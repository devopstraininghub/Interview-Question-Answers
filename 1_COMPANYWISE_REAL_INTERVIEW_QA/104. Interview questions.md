# DevOps Engineer – Encircle Tech – Interview Questions and Answers

### Q1. A Linux server has high load but low CPU usage. What could be wrong and how do you find out?

**Answer:**

High load with low CPU usage usually means processes are waiting for something other than CPU. Most commonly, it could be network I/O, blocked processes, memory pressure, or an overloaded storage system.

### Q2. Could you elaborate on how you would investigate the issue further to identify the specific cause?

**Answer:**

I would investigate in a structured order, starting with the load average and process state. First, I would check the number of CPU cores and the current load using `uptime`, `mpstat`, and `top`.

If the load is much higher than the CPU core count but CPU utilization remains low, I would check whether processes are waiting for I/O. In `top`, I would look for processes in the D state.

### Q3. Users report intermittent 500 to 504 errors behind the load balancer. How do you troubleshoot this issue?

**Answer:**

I would first determine whether the errors come from the load balancer itself or from the backend applications. I would check the load balancer access logs and metrics for error codes, affected targets, requested paths, response times, and timing patterns.

A 500 error usually indicates an application-side failure, while a 504 usually means the load balancer timed out while waiting for the backend.

### Q4. Could you explain what specific steps you would take if you determined that the issue is on the backend application side?

**Answer:**

I would first identify the affected backend targets and correlate the load balancer error timestamps with application logs. I would check whether the failure affects all instances or only specific parts or servers.

### Q5. How do you manage secrets and enforce least privilege across pipelines and workloads?

**Answer:**

I avoid storing secrets in source code, Git repositories, Docker images, Jenkins files, or plain Kubernetes manifests.

For AWS workloads, I store secrets in AWS Secrets Manager or Systems Manager Parameter Store with encryption through KMS.

For Kubernetes, I use controlled integration with Secrets Manager through the Secrets Store CSI Driver or approved external secret solutions.

I grant workloads access through IAM Roles for Service Accounts, so each service receives only the permissions it needs.

### Q6. Can you design a highly available and secure architecture for a .NET or Node.js application with a SQL database on Azure or AWS? Please describe your approach.

**Answer:**

I would design the application across multiple Availability Zones, keep the application tier stateless, and place the database in a managed, highly available service on AWS.

I would use Route 53 for DNS, CloudFront and AWS WAF at the edge, and an Application Load Balancer across at least two Availability Zones.

I would run the .NET or Node.js application on EKS, ECS, or an Auto Scaling Group with multiple replicas distributed across the zones.

On Azure, the equivalent design would use Azure DNS and Front Door or Application Gateway with WAF, along with AKS or Virtual Machine Scale Sets.

I would place the load balancer in public subnets and keep application workloads in private subnets.

For the SQL database, I would use Amazon RDS Multi-AZ or Azure SQL Database with zone and failover support.

### Q7. When would you use Ansible alongside Terraform?

**Answer:**

I use Terraform for provisioning and managing infrastructure, and I use Ansible for configuring systems and deploying applications.

For example, Terraform can create the VPC, subnets, security groups, IAM roles, and RDS.

Ansible can install packages, configure operating system dependencies, manage users, deploy application files, configure Tomcat or Node.js, and restart services safely.

### Q8. If someone manually changed a resource in the Cloud Console and Terraform now shows drift, what do you do?

**Answer:**

I would not apply the plan immediately. First, I would review the Terraform plan and identify the exact resource and attributes that changed.

I would confirm whether the manual change was authorized and understand why it was made. Then I would compare the Terraform code, variables, provider versions, state, and actual cloud configuration.

If the manual change is the desired configuration, I would update the Terraform code to match it, run `terraform plan` again, and commit the change through the normal review process.

If the manual change was unauthorized or incorrect, I would let Terraform restore the configuration defined in Git, but only after reviewing the plan and receiving the required approval.

### Q9. How do you structure Terraform for multiple environments and a team of engineers?

**Answer:**

I would keep reusable infrastructure in versioned modules and keep environment-specific configurations outside those modules.

A typical Terraform structure would have separate modules for VPC, EKS, IAM, and RDS.

For example, we can have separate environments such as development and staging.

Each environment would have a separate remote state location, such as an S3 bucket with a separate key for each environment, and DynamoDB state locking.

I would enable encryption, versioning, and restricted access on the state backend because Terraform state can contain sensitive information.

I would use modules for common resources such as VPC, EKS clusters, IAM roles, and databases. The modules would expose clear inputs and outputs, while environment folders would provide values such as instance sizes, replica counts, IP ranges, and tags.

For team collaboration, I would store Terraform code in Git and require pull requests with peer reviews.

I would also add security and policy checks using tools such as Checkov or TFSec.

The pipeline would publish the plan for review, and only an approved pipeline would run `terraform apply`. I would prevent engineers from applying directly from local machines, especially in production.

### Q10. Can you explain how traffic reaches a pod from the Internet, including the roles of Ingress, Service, kube-proxy, and DNS?

**Answer:**

DNS resolves the application name. For example, when a user requests `api.example.com`, Route 53 or another DNS provider returns the public address of the cloud load balancer.

The load balancer receives the request in EKS. An AWS Load Balancer Controller can create and manage an Application Load Balancer for Ingress resources.

The load balancer terminates TLS when configured to do so and applies listener rules.

The Kubernetes Ingress provides HTTP or HTTPS routing rules. It maps hostnames and paths to Kubernetes Services.

The Service provides a stable address across pods. It selects pods using labels and maintains a stable virtual IP and port. It also distributes traffic across the selected ready endpoints.

In AWS, the controller can use either instance targets or pod IP targets, depending on the configuration.

### Q11. How do you secure a Kubernetes cluster?

**Answer:**

I secure the cluster in layers, starting with access control, network security, workload security, image security, and monitoring.

For cluster access, I use AWS IAM with Kubernetes RBAC. IAM controls access to the AWS account and EKS authentication, while Kubernetes RBAC controls permissions inside the cluster.

I use separate roles and service accounts, follow least privilege, restrict cluster admin access, and avoid sharing credentials.

I keep the EKS control plane private where possible and restrict API server access to approved networks.

Worker nodes run in private subnets, and security groups allow only required traffic.

I also use network policies to control pod-to-pod and ingress or egress communication.

For workloads, I enforce pod security standards and prevent privileged containers unless explicitly approved.

I secure the software supply chain by scanning images for vulnerabilities using tools such as Trivy and approved registry scanning. I use trusted registries, immutable image tags, digests, and signed images where supported. CI/CD gates block critical vulnerabilities.

I never store secrets in Git or container images. I use AWS Secrets Manager or Parameter Store with KMS encryption and integrate them with Kubernetes through approved external secret solutions or the Secrets Store CSI Driver.

I use IAM Roles for Service Accounts so each workload receives only the permissions it needs.

### Q12. How do you achieve zero-downtime deployments in Kubernetes?

**Answer:**

I start by making the application highly available, so I run multiple replicas across Availability Zones. I also ensure the application remains stateless and stores state in highly available services.

For a standard rolling deployment, Kubernetes keeps the existing capacity available while the new pod starts, using settings such as `maxSurge` and `maxUnavailable: 0`.

This allows Kubernetes to create an additional pod during the update.

I configure accurate readiness probes so Kubernetes sends traffic only to pods that are ready. I use liveness probes to restart unhealthy containers and startup probes for applications that need more time to initialize.

### Q13. A pod keeps restarting and also gets OOMKilled intermittently. How do you investigate and fix it?

**Answer:**

I would first confirm the termination reason and determine whether the container exceeds the memory limit. In the pod description, I would look for the reason, exit code, restart count, and recent events.

I would also check current and historical memory usage.

### Q14. What steps would you take to resolve the OOMKilled issue once you have identified the cause?

**Answer:**

I would first separate immediate mitigation from the permanent fix.

For immediate mitigation, I would reduce customer impact by scaling the deployment if the cluster has capacity.

If the issue started after a release, I would roll back to the last known good version.

If the container has an incorrect or low memory limit, I would update the resource settings through Git and the normal deployment process.

I would not increase the limit blindly. I would compare the limit with actual usage, node capacity, and the application's normal memory profile.

I would also verify that the node has enough allocatable memory and scale the node group if the cluster lacks capacity.

For the permanent fix, I would investigate the application for memory leaks, unbounded caching, large payloads, and excessive concurrency.

I would review application logs and memory metrics and use a heap dump or runtime profiling when appropriate.

For Node.js, I would review heap usage and garbage collection behaviour. For .NET, I would analyze managed heap and garbage collection metrics.

### Q15. A bad release reached production at 2:00 AM. Walk through detection, rollback, and prevention.

**Answer:**

I would first confirm the customer impact and declare the appropriate incident severity.

I would check CloudWatch, Prometheus, and Grafana for error rates, latency, traffic, pod restarts, resource usage, and load balancer health.

I would compare the timing with the deployment and review application logs and Kubernetes events.

If the release clearly caused the issue, I would prioritize service restoration over detailed investigation.

For a Kubernetes deployment, I would check the rollout history and roll back to the last known good version.

If Argo CD manages the application, I would revert the Git commit or Helm version and allow Argo CD to reconcile the cluster.

I would verify the previous image, configuration, and secrets and restore them correctly.

### Q16. Your pipeline takes 40 minutes and developers are complaining. How do you speed it up?

**Answer:**

I would first measure the pipeline by stage instead of optimizing based on assumptions.

I would identify whether the main delay comes from dependency downloads, builds, tests, security scans, Docker image creation, artifact publishing, or deployment.

Then I would apply the following improvements:

- Run independent stages in parallel.
- Run unit tests, linting, static analysis, and security scans at the same time when they do not depend on each other.
- Cache Maven dependencies, NPM packages, Docker layers, and scanner databases where appropriate.
- Use reliable internal repositories such as Nexus or JFrog to avoid downloading the same dependencies repeatedly.
- Use efficient, prebuilt Jenkins agents with the required tools already installed.
- Optimize the build context and use proper Docker images.
- Use multi-stage Dockerfiles to improve Docker image builds.
- Improve test execution by running fast unit tests on every commit and parallelizing test suites.
- Optimize security scans by running fast checks early, reusing scanner caches, and scanning only changed components where supported.
- Avoid unnecessary deployments.
- Reuse artifacts.
- Move common logic into Jenkins shared libraries.
- Monitor stage durations over time.

### Q17. Describe a pipeline you designed. What decisions did you make and what would you change now?

**Answer:**

I designed a Jenkins pipeline for a containerized application deployed to EKS through Helm and Argo CD.

The pipeline started when a developer created or updated a pull request. It checked out the code, ran Maven builds and unit tests, performed code quality checks with SonarQube, scanned dependencies with Black Duck, built a Docker image, and scanned the image.

It then published the approved artifact to JFrog or Nexus.

After the pull request passed review and quality gates, the pipeline built the image once with an immutable tag based on the commit SHA.

It updated the deployment configuration in Git. Argo CD detected the Git changes and synchronized the application with the target EKS environment.

The pipeline monitored the rollout and ran smoke tests after deployment.

I used Jenkins Shared Libraries to centralize common stages such as checkout, build, testing, scanning, artifact publishing, and approvals.

The main decisions were to build an artifact only once, promote the same artifact across environments, keep deployment configuration in Git, use Argo CD for GitOps, and place security checks before deployment approval.

I also used environment-specific Helm values while keeping the chart reusable.

For production, I would use canary or blue-green deployments with automated rollback based on the error rate.

### Q18. How do you stay current with new technologies and best practices, particularly concerning cloud platforms, containerization, or automation? Can you give an example of a new tool or technique you recently learned and applied?

**Answer:**

I stay current through official AWS and Kubernetes documentation, release notes, technical labs, architecture reviews, incident learnings, and hands-on testing in non-production environments.

I focus on understanding the operational problem a technology solves rather than adopting tools only because they are new.

Recently, I started improving my knowledge of GitOps with Argo CD and progressive Kubernetes delivery.

I applied the approach by keeping Helm manifests and environment values in Git, using Argo CD to compare the desired state with the live EKS state, and controlling deployments through reviewed Git changes instead of manual cluster updates.

I also worked with Jenkins Shared Libraries to standardize pipeline stages and integrated security checks such as SonarQube, Black Duck, and Trivy before deployment approval.

For cloud and Kubernetes learning, I regularly review EKS upgrade guidance, IAM and workload identity patterns, CNI and CSI changes, and security recommendations.

I test changes in a lower environment before introducing them into production.

I also learn from production incidents and post-incident reviews. When an issue occurs, I look for improvements in automation, observability, deployment safety, and rollback.

For example, centralized logging with Fluent Bit and Fluentd, along with proactive Prometheus and CloudWatch alerting, helped improve troubleshooting and reduce MTTR by more than 30%.
