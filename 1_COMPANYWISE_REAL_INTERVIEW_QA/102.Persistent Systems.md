# DevOps Interview Questions and Answers

### Q1. Tell me about yourself.

**Answer:** I have around 9 years of overall IT experience, including 6 years focused on DevOps and AWS. I currently work as a Senior DevOps Engineer, supporting a banking application project for SunTrust.

My responsibilities include AWS infrastructure, CI/CD pipelines, Kubernetes deployments, monitoring, automation, and production support.

I work with AWS services such as EC2, VPC, S3, RDS, IAM, load balancing, and Auto Scaling. I also manage AWS EKS clusters, including upgrades, node groups, autoscaling, high availability, and application deployment using Helm.

For infrastructure automation, I use Terraform and Ansible. I have created reusable Terraform modules such as VPC, EKS, and IAM.

### Q2. You mentioned managing AWS EKS clusters, including upgrades and autoscaling. Can you explain your approach to handling Kubernetes Operators and Custom Resource Definitions (CRDs) in your deployments?

**Answer:** In my EKS deployment, I treat Operators and CRDs as platform dependencies, so I manage them separately from application workloads.

First, I review the Operator documentation and confirm compatibility with the EKS and Kubernetes versions. I check the required CRDs, RBAC permissions, service accounts, webhooks, and AWS integrations.

I also verify that the Operator supports the required namespace and workload configuration.

I normally deploy Operators using Helm with versioned chart values stored in Git.

For GitOps environments, I manage the Helm release and custom resources through Argo CD.

After deployment, I evaluate the Operator pods, CRDs, custom resources, events, and controller logs.

### Q3. How do you handle Operator upgrades and rollback scenarios in your Kubernetes environments?

**Answer:** I handle Operator upgrades as controlled platform changes because Operators manage other Kubernetes resources, and their CRDs can affect dependent workloads.

First, I review the Operator release and confirm compatibility with the EKS version, Kubernetes APIs, CRD schemas, Helm charts, RBAC permissions, webhooks, and AWS integration.

I test the upgrade in a lower environment before promoting it to production.

I keep the Operator version and Helm values in Git through Argo CD. I deploy the approved version and monitor the Operator pods, CRDs, custom resource events, and controller logs.

I also verify that the Operator continues reconciling resources successfully and that dependent applications remain healthy.

Before the upgrade, I capture the current Helm release details and back up important custom resource definitions and custom resource configurations according to the platform process.

I also confirm that the Operator supports the required upgrade and rollback path.

### Q4. How do you troubleshoot and resolve issues if an Operator deployment causes disruptions in production?

**Answer:** First, I focus on customer impact and service restoration.

I check whether the issue affects the Operator itself, the custom resources it manages, or the dependent application.

I review Argo CD sync history, recent Git changes, Helm release details, Kubernetes events, Operator pod status, and controller logs.

I also check the affected custom resources, webhook status, CRD conditions, RBAC permissions, and any changes to deployed services or AWS resources.

If the application is impacted, I check pod health, readiness and liveness probes, service endpoints, load balancer target health, and application logs.

I also review CloudWatch, Prometheus, and Grafana metrics to understand the scope of the disruption.

### Q5. How do you incorporate automation or alerting to proactively detect and respond to Kubernetes Operator or CRD failures before they impact production?

**Answer:** I use health checks, metrics, logs, and Git validation to detect issues early.

First, I monitor the Operator deployment itself. I create alerts for unavailable replicas, pod restarts, CrashLoopBackOff, failed readiness probes, high resource usage, and abnormal controller behavior.

I also monitor Kubernetes events for failed reconciliations, webhook errors, permission issues, and repeated resource updates.

For CRDs and custom resources, I monitor their status conditions and reconciliation failures.

I create alerts when a resource remains in a failed or pending state longer than the expected time, when the Operator stops updating status, or when dependent resources are not created or become unhealthy.

I use Prometheus and Grafana for Kubernetes and Operator metrics and CloudWatch for AWS resources.

I use centralized logging with Fluent Bit and Fluentd so I can search controller logs and correlate failures with deployments or infrastructure changes.

### Q6. How do you design and manage CI/CD pipelines using Git and related tools to ensure smooth and reliable software deployments?

**Answer:** I design CI/CD pipelines around version control, automation, security testing, approvals, and reliable deployment.

I use Git as the source of truth. Developers work on feature branches and submit pull requests for review. The pipeline is triggered by Git changes.

I keep application code, pipeline definitions, Helm charts, and infrastructure code versioned and reviewed.

In Jenkins, I use shared pipeline logic for common stages such as checkout, build, testing, static analysis, artifact creation, security scanning, and deployment.

For Java applications, Maven handles the build and test process. I publish versioned artifacts to an artifact repository such as Nexus.

Before deployment, I include quality and security checks such as SonarQube for code quality, code analysis, and dependency analysis.

I use approval gates when the pipeline promotes changes to higher environments.

### Q7. How do you manage branching strategies and Git workflows within your CI/CD process to handle multiple development streams and releases?

**Answer:** I use branching strategies that keep deployment work isolated while maintaining a stable and deployable main branch.

Developers create feature branches from the main branch. They make focused changes and raise pull requests for peer review.

The pull request pipeline runs build validation.

For larger releases, I use release branches when the planned features are ready for stabilization.

The release branch accepts only approved bug fixes, testing changes, and release updates.

After validation, I merge it into the main branch and create a version tag.

I also merge important fixes back into the development branch so that the changes are not lost.

For urgent production issues, I use short-lived hotfix branches.

### Q8. How do you handle merge conflicts and ensure smooth integration during these merges, especially under tight release timelines?

**Answer:** I reduce merge conflicts by keeping branches short-lived, making small focused commits, and regularly synchronizing feature branches with the target branch.

I also encourage developers to avoid changing the same files unnecessarily and to raise pull requests early.

When a conflict occurs, I first identify the target branch and understand the purpose of those changes.

I update my local branch, fetch the latest changes, and rebase or merge the target branch into the feature branch according to the team's Git workflow.

I resolve conflicts carefully, keeping the intended behavior from both changes rather than accepting one side blindly.

After resolving conflicts, I run formatting checks, tests, build validation, code quality checks, and security scans.

Then I push the updated branch and allow the pull request pipeline to run again before requesting approval.

### Q9. Can you describe your experience using infrastructure as code tools like Terraform or Ansible to automate infrastructure provisioning and management?

**Answer:** I use Terraform for infrastructure provisioning and Ansible for configuration management and application automation.

With Terraform, I have created reusable modules for AWS resources such as VPC, EKS, IAM, and supporting infrastructure.

I keep the Terraform code in Git and separate reusable module logic from environment-specific variables.

This allows me to use the same structure across development, testing, and production while changing only the required inputs.

I use a remote Terraform backend with state locking so that multiple environments do not modify the same state at the same time.

With Ansible, I create playbooks and reusable roles for server configuration and application deployments.

I use it to install packages, manage configuration files, deploy applications, restart services, and perform operational tasks across Linux or Windows environments.

I design Ansible tasks to be idempotent, so running the playbook multiple times produces the same expected state without unnecessary changes.

### Q10. How do you handle version control, testing, and validation of your IaC code to ensure safe and reliable infrastructure changes?

**Answer:** I keep all Terraform modules, environment configurations, Ansible playbooks, roles, and variable files in Git.

I use feature branches and pull requests. Every change receives peer review before it reaches the main branch.

For Terraform, I run formatting and validation checks first, followed by a plan. I review the plan carefully to confirm that it creates, updates, or destroys only the expected resources.

For Ansible, I validate YAML syntax, check inventory and variable values, and run playbooks in a lower environment before production.

I design tasks to be idempotent and use check mode where appropriate to review changes without applying them.

### Q11. Can you describe a challenge you faced with infrastructure automation and how you resolved it?

**Answer:** One challenge I faced was managing infrastructure consistently across multiple environments while avoiding duplicate Terraform code and unexpected changes.

Different environments had different networking, IAM, and EKS requirements, and manual changes could also create drift between the actual AWS resources and the Terraform state.

I addressed this by creating reusable Terraform modules for resources such as VPC, EKS, and IAM.

Before applying changes, I run formatting and validation checks and review the Terraform plan carefully.

When the plan showed unexpected changes, I checked the state, provider versions, variables, recent code changes, and possible manual drift instead of applying it immediately.

I also used a remote backend with state locking to prevent concurrent updates.

### Q12. Can you describe your experience implementing observability and monitoring solutions with tools like Prometheus, Grafana, or OpenTelemetry?

**Answer:** I work with Prometheus, Grafana, CloudWatch, ELK, Fluent Bit, Fluentd, and New Relic to monitor infrastructure, Kubernetes platforms, applications, and production servers.

For EKS, I monitor cluster and workload health, including node status, pod restarts, CPU and memory usage, resource limits, deployment availability, readiness failures, and application latency.

Prometheus collects the metrics, and Grafana provides dashboards for Kubernetes, application, and infrastructure trends.

I use CloudWatch for AWS services such as EC2, load balancers, Auto Scaling, RDS, and other important resources.

I review metrics, logs, and alarms to identify issues such as high utilization, unhealthy targets, database performance problems, and infrastructure failures.

For centralized logging, I have worked with Fluent Bit and Fluentd to collect logs for Kubernetes workloads and forward them to a centralized logging platform.

This allows me to search application and container logs and correlate them with deployments, alerts, and infrastructure events.

### Q13. How do you set up alerting and escalation policies to ensure timely response to critical incidents?

**Answer:** I start by defining alerts around customer impact and service objectives, not just individual resource thresholds.

I use Prometheus and Grafana for Kubernetes and application metrics, and CloudWatch for AWS services.

For example, I create alerts for high error rates, increased latency, unavailable replicas, failed readiness probes, CrashLoopBackOff, node pressure, unhealthy load balancer targets, high database connections, and resource saturation.

I also monitor service-level indicators such as availability and request success rate.

Each alert includes the affected service, environment, severity, current value, start time, and useful diagnostic information.

I classify alerts by severity and criticality. Critical alerts require immediate notification through the appropriate incident channel and on-call process.

Lower-severity alerts create a ticket for investigation during business hours.

For escalation, the primary on-call engineer receives the alert first. If there is no acknowledgement within the defined time, it is escalated.

### Q14. How do you leverage observability data to troubleshoot and optimize system performance proactively?

**Answer:** I use observability data to understand what is failing, when it started, which component is affected, and how customers are impacted.

I begin with the main service indicators, such as request rate, error rate, latency, availability, and saturation.

I use Grafana and Prometheus for Kubernetes and application metrics and CloudWatch for AWS services such as EC2 and load balancers.

Then I correlate the metrics with logs and events.

For example, if latency increases, I check pod CPU and memory, recent deployment changes, load balancer target health, database connections, slow queries, and application errors.

I use Fluent Bit, Fluentd, ELK, or CloudWatch logs to search and correlate application and infrastructure logs.

For Kubernetes, I check pod restarts, readiness failures, resource requests and limits, and HPA.

### Q15. Can you describe a complex production issue you resolved, your troubleshooting approach, and the tools you used?

**Answer:** One production issue involved application instability after a deployment. Users experienced failures, and some Kubernetes pods were restarting.

My first priority was understanding customer impact and restoring the service.

I checked Grafana and Prometheus for error rates, latency, pod restarts, CPU, memory, and node health.

I also reviewed CloudWatch metrics and load balancer target health to confirm whether the issue was limited to Kubernetes or affected the AWS infrastructure.

Next, I checked the deployment history, Kubernetes pod descriptions, current and previous container logs, readiness and liveness probe failures, resource configurations, ConfigMaps, Secrets, and application startup messages.

I also used centralized logging through Fluent Bit and Fluentd to correlate application errors with the deployment time.

The investigation showed that the new deployment was not becoming ready, which caused unhealthy targets and request failures.

### Q16. What steps did you take to identify the root cause and implement a fix to restore stability?

**Answer:** First, I confirmed the impact by checking the error rate, latency, pod restarts, and readiness status.

I compared the new deployment with the previous known-good version.

I reviewed the deployment manifest, Helm values, ConfigMaps, Secrets, container images, and readiness probe configuration.

I also checked Kubernetes events and both current and previous container logs to identify the first meaningful error.

The logs and readiness failures showed that the new pods were not becoming ready. Kubernetes did not send traffic to them, and the load balancer marked the targets as unhealthy.

To restore service, I used the rollback process through Helm and Argo CD and returned the application to the previous known-good version.

After service restoration, I worked with the application team to correct the configuration and health-check issues.

We tested the fix in the lower environment, validated the deployment and probes, and promoted it through the normal CI/CD process.

### Q17. How do you document and share production incident learnings to prevent recurrence and improve team response?

**Answer:** After restoring the service, I document the incident in the appropriate ticketing or incident management system.

I include the customer impact, start and end time, affected services, detection method, timeline of actions, investigation findings, mitigation, root cause, and recovery validation.

I clearly separate the root cause from contributing factors.

For example, I document whether the issue came from application configuration, deployment settings, readiness probes, infrastructure, or an operational process.

I also record the exact changes made during recovery, such as the Helm or Argo CD rollback, and the checks used to confirm service stability.

I include relevant dashboards, logs, Kubernetes events, and deployment references so that the investigation remains traceable.

After the incident, I conduct a blameless review with the deployment, SRE, and support teams.
