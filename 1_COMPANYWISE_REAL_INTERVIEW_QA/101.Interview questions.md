### Q5. When is a workload a good fit for Spot Instances?

**Answer:** I use Spot Instances for workloads that can tolerate interruptions and do not require continuous availability on a specific instance.

Examples include batch processing, CI/CD rebuild agents, data processing, and testing environments.

I avoid Spot Instances for critical workloads, such as databases, primary production services, or applications that cannot handle interruptions.

The main benefit is significant cost reduction, but I always combine Spot Instances with On-Demand capacity for critical high-availability workloads.

### Q6. How would you keep workload access to a managed AWS service private and off the public Internet?

**Answer:** I would use VPC endpoints so that workloads can access AWS managed services through the private AWS network instead of public endpoints.

I would use Gateway Endpoints for services such as DynamoDB. For services such as Secrets Manager or ECR, I would use Interface Endpoints powered by AWS PrivateLink.

I would keep workloads in private subnets, configure the required route tables or endpoint subnets, and restrict access using security groups and endpoint policies.

I would also verify DNS resolution and ensure the workload does not require an internet gateway for accessing those services.

### Q7. How would you manage KMS keys for encrypted data in a shared AWS environment?

**Answer:** I will use customized KMS keys with clear ownership, separation of duties, and least-privilege access.

I will create separate keys for different environments or data classifications, such as development, staging, and production.

I would control access using both KMS key policies and IAM policies, allowing only the required roles related to cryptographic operations.

I would use AWS Organizations and KMS grants or cross-account key policies when other accounts need access.

I would separate key administrators from application users and enable automatic key rotation.

I would also review key permissions and ensure services such as S3 and Secrets Manager use the correct KMS key.

### Q9. Why might a pod still receive traffic before its application is actually ready, and how would you prevent that?

**Answer:** A pod might receive traffic before the application is ready if the readiness probe is missing or incorrectly configured.

Kubernetes may see the container as running, but the application may still be starting or waiting for the database or another dependency.

I would configure proper readiness probes that check the application's actual readiness. Until the probe succeeds, the pod does not receive traffic.

I would also configure suitable startup probes for applications with a slow startup time.

I would configure liveness probes separately to restart the container only when it is running but no longer healthy.

### Q10. How does a Pod Disruption Budget help during node maintenance?

**Answer:** A Pod Disruption Budget (PDB) protects application availability during voluntary disruptions, such as cluster updates and planned maintenance.

I define either a minimum number of available pods or a maximum number of unavailable pods.

For example, I can request that at least two replicas remain available when a node is drained.

At the same time, PDB does not protect against every failure. It mainly controls voluntary evictions, not sudden node failures, crashes, or hardware failures.

I also need enough replicas, proper distribution across nodes or availability zones, and correct readiness probes.

### Q11. What RBAC mistake most often gives a team more Kubernetes access than intended?

**Answer:** The most common mistake is assigning broad permissions, especially binding the cluster-admin role when a user or service account only needs access to a specific namespace or resource.

I avoid this by using least privilege. I create namespace-scoped Roles and RoleBindings whenever possible.

I use ClusterRole only when access must span multiple namespaces.

I also review service account permissions regularly.

I validate access using commands such as `kubectl auth can-i` and audit privileges through Kubernetes and AWS logging.

### Q12. What upgrade sequence do you follow in Kubernetes to avoid upgrade problems?

**Answer:** I follow a controlled sequence.

First, I review the target Kubernetes versions, deprecated APIs, application compatibility, and compatibility of add-ons such as the CSI driver, autoscaler, Helm charts, and monitoring components.

Next, I test the upgrade in a non-production environment. I validate application requirements, networking, storage, autoscaling, workloads, and monitoring.

I also confirm backups, rollback steps, maintenance windows, and communication plans.

For an EKS upgrade, I normally upgrade the control plane first, then update the managed add-ons such as the VPC CNI, CoreDNS, and Kubernetes proxy.

After that, I upgrade the worker nodes in a controlled manner before replacing nodes. I verify pod distribution and workload availability.

### Q13. What problem does provider version pinning solve in Terraform?

**Answer:** Provider version pinning prevents unexpected changes caused by automatically downloading a new provider version.

A newer version can change resource behavior, validation rules, defaults, or API compatibility and create unexpected deployment failures.

I define the required provider version in the Terraform configuration and commit the dependency lock file so that team members and CI/CD pipelines use the same provider version.

I upgrade providers by reviewing release notes, testing in the lower environment, running Terraform plan, and then promoting through the normal approval process.

### Q14. How would you handle drift when someone changes resources manually outside Terraform?

**Answer:** I would first identify the drift without applying changes. I would run Terraform plan and review which resources differ from the Terraform state and configuration.

Then I would confirm who made the change and whether it was approved.

I would check AWS audit logs, such as CloudTrail, and compare the live resources with the Terraform code.

I would apply the plan through the normal approval process to restore the desired state.

If the manual change is valid, I would update the Terraform configuration accordingly. I would not edit the state file manually unless there was a specific state management issue.

### Q15. What risks show up when you import an existing cloud resource into Terraform?

**Answer:** The main risk is that importing a resource only adds it to the Terraform state. It does not automatically create the correct Terraform configuration.

If the configuration does not match the live resources, the next Terraform plan can show unexpected updates, replacements, or resource recreation.

I would first back up the state and confirm the correct workspace and account.

Then I would import the resources using their existing IDs, write the matching Terraform configuration, and run Terraform plan to validate the state and live resources.

I would pay close attention to immutable attributes, encryption, networking, IAM policies, dependencies, and provider defaults.

I would not apply changes until the plan is fully understood and reviewed.

### Q16. How do you keep IAM roles and policies secure and maintainable in Terraform?

**Answer:** I follow least privilege and keep IAM definitions modular and version-controlled.

I create separate Terraform modules for roles, policies, and policy attachments with clear inputs and outputs.

I avoid using wildcard permissions unless the service specifically requires them. I grant only the required actions on specific resources and use conditions where appropriate, such as source VPC, account IDs, tags, or encryption keys.

I separate IAM roles by workload and environment, and I use roles instead of long-lived access keys for AWS services and workloads.

Before applying changes, I review the Terraform plan through pull requests and run security checks using tools such as tfsec and policy-as-code controls.

I also validate IAM policies using IAM policy tools.

### Q17. If Jenkins occasionally misses source control webhooks, what would you check first?

**Answer:** I would first confirm whether the issue affects one repository or all repositories.

I would check the job trigger configuration, webhook URL, webhook settings, and recent webhook delivery issues.

Then I would review Jenkins and the source control system logs for HTTP status codes, timeout errors, authentication failures, or connection errors.

I would verify that the Jenkins endpoint is reachable from the source control platform and check load balancers, security groups, firewalls, DNS, reverse DNS, and proxy configurations.

I would also check whether Jenkins is overloaded, whether the webhook plugin is healthy, and whether jobs are being queued or throttled.

If the webhook is delivered successfully but the job does not start, I would inspect the job filter and branch rules, credentials, and pipeline configuration.

### Q18. What do you consider a safe way to move an artifact from build to test and release in Jenkins?

**Answer:** I build the artifact once and promote the same immutable artifact to each environment.

I do not rebuild it separately for test, staging, and production because that can produce different artifacts.

After the build, I run unit tests, code quality checks, security scans, and dependency checks.

I publish the versioned artifact to a controlled repository using unique versioning or a build identifier.

The test environment deploys that exact artifact. I validate health, integration tests, smoke tests, and monitoring results.

Promotion to the next environment requires defined approvals and quality gates for production.

I use the same verified artifact and deploy it through the approved pipeline or GitOps process.

### Q19. How would you segment subnets of development, staging, and production so they are isolated in the same AWS environment?

**Answer:** I would use separate AWS accounts for development, staging, and production whenever possible.

I would use separate VPCs and private subnets for the application, data, and management layers.

I would keep the production database and sensitive services private and control access using security groups, NACLs, route tables, and VPC endpoints.

I would also separate IAM roles, KMS keys, Secrets Manager secrets, and CI/CD permissions for each environment.

Developers would not receive direct production access. Production changes would go through approved pipelines and controlled processes.
