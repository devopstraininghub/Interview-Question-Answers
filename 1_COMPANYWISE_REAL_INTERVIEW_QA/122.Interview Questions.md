### Q7. Suppose a container is continuously failing in a large Kubernetes cluster. What troubleshooting steps would you follow?

**A:** First, I confirm the namespace, deployment, pod name, container name, start time, and customer impact.

I check whether only one pod is failing or whether the entire deployment is affected.

Then I inspect the pod details using `kubectl describe pod` within the namespace. I look for events such as OOMKilled, failed probes, image pull errors, mount failures, permission errors, or node pressure.

Next, I check the current and previous container logs, especially the previous logs when the container restarts.

I classify the failure into common areas:

- **OOMKilled:** Check memory requests, limits, and container memory usage.
- **CrashLoopBackOff:** Inspect the application exit code and startup command.
- **Readiness or liveness probe failures:** Verify the probe path, timeout, and initial delay.
- **ImagePullBackOff:** Verify the image tag and registry.

### Q9. Can you explain the request flow for an Internet-facing application and how you troubleshoot each component?

**A:** First, the client resolves the application domain through Route 53, which returns the ALB address, usually through an alias record.

For Route 53, I check the record name, record type, target hosted zone, health checks, routing policy, and DNS resolution. I also verify that the record points to the correct load balancer and that DNS changes have propagated.

Next, when the request reaches the Application Load Balancer, I check the listener on port 80 or 443, listener rules, certificates, target groups, security groups, and target health.

I also review ALB metrics and access logs for status codes, rejected connections, and unhealthy targets.

### Q11. If an application keeps loading in the browser and eventually times out after 30 seconds, what error code might you see and what could be the reason?

**A:** The most common response from an ALB is HTTP 504 Gateway Timeout.

This means the ALB forwarded the request to the target, but the target did not respond within the configured idle timeout. The browser may also show a generic network error or timeout message instead of displaying the 504 directly.

Possible causes include:

- The API is slow or stuck.
- The application is waiting on a database query.
- RDS has high CPU usage or slow queries.
- The pod is overloaded, restarting, or failing to process the request.
- Kubernetes routing is incorrect.
- There may be an issue with the ALB target.

### Q17. Can you explain rolling deployments and blue-green deployments in Kubernetes?

**A:** A rolling deployment gradually replaces the old application pods with new pods. Kubernetes starts new pods with the updated version, waits for them to become ready, and then terminates the old pods in batches.

In blue-green deployment, we use two separate environments. The blue environment runs the current production version, and the green environment runs the new version.

I deploy the green version separately and validate its services, health checks, configurations, database connectivity, and smoke tests. Then I switch traffic to green through Service, Ingress, or ALB routing configuration.

If the green version causes errors, I switch traffic back to blue. This provides a fast and simple rollback path.
