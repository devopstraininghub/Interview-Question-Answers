**Q5. Suppose you need to provision an ECS cluster with worker nodes. Would you prefer EC2 or Fargate?**

**Answer:** If the requirement involves provisioning an ECS cluster with worker nodes, I would prefer EC2 because it gives me control over the underlying infrastructure.

First, I would create an ECS cluster, provision EC2 instances using an Auto Scaling Group, and attach them to the ECS cluster through an ECS Capacity Provider.

I would choose EC2 or Fargate based on the requirement. Since the requirement involves managing worker nodes, I would prefer EC2.

With Fargate, AWS manages the infrastructure, so I don't have direct control. With EC2, I have control over the instance type, CPU configuration, memory, and network according to the requirement. Cost is also a consideration.

**Q6. How does networking take place in an EKS cluster? How would two microservices communicate with each other?**

**Answer:** Suppose I have Microservice A and Microservice B running in separate pods in an EKS cluster.

I would first configure a Kubernetes ClusterIP service to enable communication between them.

I would ensure that both microservices have their respective deployments and pods running successfully.

Then I would create a ClusterIP service for Microservice B, exposing its application port, for example, port 80.

I would define a selector matching the labels of Microservice B's pods and configure the service port.

From Microservice A, I would access Microservice B using its internal Kubernetes DNS name.

**Q7. Apart from ClusterIP, what other networking configurations would you use?**

**Answer:** I would use network policies to ensure that Microservice A has permission to communicate with Microservice B.

I would configure ingress rules for Microservice B to allow traffic from Microservice A.

I would also configure egress rules for Microservice A to allow outgoing traffic towards Microservice B on port 80.

I would use pod selectors to match the labels.

**Q8. How many security groups are required for an EKS cluster?**

**Answer:** There is no fixed number of security groups required. It depends on the cluster architecture and network requirements.

AWS automatically provides a security group when creating an EKS cluster. It manages communication between the EKS control plane and worker nodes.

For an EKS cluster with EC2 worker nodes, I generally consider two types of security groups:

1. Cluster security group.
2. Worker node security group.

**Q11. Why do you create volumes in a Kubernetes cluster?**

**Answer:** We use persistent storage to store application data because containers are temporary. When a container or pod restarts, the data inside the container can be lost.

We use Persistent Volumes and Storage Classes to maintain persistent storage.

First, I would create a StorageClass to define the type of storage required. In AWS EKS, we commonly use the EBS CSI driver to provision EBS volumes dynamically.

The second is PVC, which stands for Persistent Volume Claim. We create a PVC to request storage, for example, 10 GB of storage with ReadWriteOnce access mode.

The third is PV, which stands for Persistent Volume. It represents the storage provided to the application.

**Q13. How would you use a certificate as a Kubernetes Secret inside your application?**

**Answer:** Once we receive the `.p12` certificate, we would create a Kubernetes Secret containing the certificate file instead of keeping it directly inside the Kubernetes image or pod.

Then we mount the Secret as a volume inside the application pod.

We configure the Secret volume in the Kubernetes deployment file.

**Q14. What is the use of a DaemonSet?**

**Answer:** We mainly use DaemonSets for node-level monitoring, networking components, and logging.

For example, if we have five worker nodes in our cluster, we use a DaemonSet to ensure that a pod runs on each eligible node.

When a new worker node is added, Kubernetes automatically creates a pod on that node. Similarly, when a worker node is removed, the DaemonSet removes the corresponding pod.

Recently, I worked on monitoring using a DaemonSet for the Prometheus Node Exporter.

**Q19. Suppose you need to create a Kubernetes cluster using Terraform. How would you proceed using Terraform modules?**

**Answer:** I would organize my Terraform project into reusable modules.

I would create separate modules for VPC, EKS, node groups, and environments such as Dev and QA.

For example, my EKS module would accept parameters such as cluster name, Kubernetes version, subnet IDs, node group instance type, and scaling configuration.

I would configure the EKS resources inside the module.

I would separate environments such as Dev and QA while reusing the same modules.

For multiple AWS regions, I would configure provider blocks and maintain separate regional VPC, subnet, and IAM configurations.

I would also use an S3 remote backend with separate state keys to maintain the infrastructure state files.

**Q20. How would you make Terraform modules reusable across multiple environments and regions?**

**Answer:** To support Dev, QA, and Production environments, I would use reusable Terraform modules.

I would organize the project with separate modules for VPC, EKS, and node groups.

I would configure the EKS module with the required parameters, including cluster name, Kubernetes version, subnet IDs, node group instance type, and scaling configuration.

I would use separate `.tfvars` files for each environment, such as `dev.tfvars`, `qa.tfvars`, and `prod.tfvars`.

**Q21. How would you deploy the same infrastructure in multiple AWS regions?**

**Answer:** For multiple regions, I would use provider blocks with aliases.

I would define two providers, for example, primary and secondary, and call the same module for both regions.

In the main Terraform file, I would call the module for the primary region and the secondary region using the respective provider aliases.

I would maintain separate subnet IDs and other regional configurations through variables or data sources.

This allows us to deploy the same infrastructure in multiple AWS regions without duplicating the module code.

**Q22. What is the use of the `output.tf` file?**

**Answer:** It displays information without going into AWS. We can get the required information through the output block.

**Q23. Suppose you need to pass information from one Terraform module to another module. How would you do it?**

**Answer:** We use an output block to get information from one module.

For example, if I have subnet IDs, I use an output block to expose the subnet IDs from the VPC module. Then I use that information in another module.

**Q24. What are the benefits of using Terraform data sources?**

**Answer:** We use a data block to fetch information about existing infrastructure in AWS without creating or modifying anything.

For example, if we already have a VPC in AWS and need to deploy an EKS cluster in that existing VPC, instead of creating another VPC, I can use the existing VPC through a data block.

This allows us to reuse existing infrastructure and retrieve its information.
