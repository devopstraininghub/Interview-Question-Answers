## Q6. Was the response time measured for an individual microservice or for the entire request?
**Ans:** In my setup, I primarily monitored response time at the individual microservice level.
Each microservice exposed Prometheus metrics such as response time, request duration, HTTP status codes, and error rates.
The response time of Service A measured the time from when it received a request until it returned a response. If Service A called Service B, its observed latency also included the time spent waiting for those downstream synchronous calls.
However, that metric alone did not show how much time Services B and C individually contributed.
## Q7. Have you considered tracking the complete request instead of only the response time of individual microservices?
**Ans:** For microservices, I would track both end-to-end latency and individual service latency because they answer different questions.
## Q8. How would you monitor the end-to-end latency of a single API communicating with multiple services?
**Ans:** In that case, I would implement distributed tracing using OpenTelemetry.
When an API receives a request at the entry service, I would create or accept a trace ID and propagate the trace context through every downstream service using standard HTTP trace headers.
I would instrument each microservice with the OpenTelemetry SDK. Each service would create spans for important operations, including inbound requests, outbound HTTP calls, and database calls.
That would give me one trace showing the complete path from Service A through all the downstream services.
## Q9. What is the major difference between TCP and UDP? How would you decide which one a service should use?
**Ans:** I decide based on the application's communication requirements.
I choose TCP when the service requires reliable and ordered delivery because TCP establishes a connection, detects packet loss, retransmits missing data, and preserves order.
For HTTP and HTTPS APIs, database connections, SSH, and most microservice communication, I would use TCP.
I choose UDP when low transport overhead and lower latency are more important than guaranteed delivery.
UDP does not provide connection establishment, acknowledgements, or ordering at the transport level.
Common use cases include DNS queries, gaming, and real-time media.
## Q10. For an e-commerce payment process, would you choose TCP or UDP?
**Ans:** In this scenario, I would choose TCP, specifically HTTPS over TCP.
Even though payments need a fast response, I need reliable, ordered, and secure communication because I cannot tolerate a lost or corrupted payment transaction.
I would optimize latency through persistent connections, connection pooling, proper timeouts, and efficient API processing rather than sacrificing reliability by using UDP.
## Q11. What is a persistent connection?
**Ans:** A persistent connection means reusing an existing network connection for multiple requests instead of creating a new connection for every request.
For example, with HTTPS, creating a new connection requires a TCP handshake before application data can flow.
If I close the connection after every API call, I repeatedly pay the connection setup cost.
With persistent connections, such as HTTP Keep-Alive, I keep the established connection open and reuse it for subsequent requests.
This reduces connection setup overhead and improves latency, especially when one microservice frequently communicates with another service or an external API.
## Q12. Suppose you have 78 or 80 microservices communicating with a single database, and you frequently receive alerts that database connections are exhausted. How would you solve this challenge?
**Ans:** Once I confirm through RCA that connection exhaustion is the issue, I would first stabilize production by identifying services with abnormal connection usage and safely reducing excessive connections where possible.
### Q13. How would you identify whether a database connection is being used or is idle? Which metrics or logs would you check?
**Ans:** For PostgreSQL, I would inspect `pg_stat_activity`. It shows each connection's application, client address, state, and how long it has remained in that state.
I would specifically look for connections that have been idle for a long time and idle-in-transaction sessions because those are more problematic.
I would not terminate a connection simply because it is currently idle, because a healthy connection pool can maintain idle connections.
## Q14. Suppose all 200 database connections have been active for 24 hours. How would you identify which connections should be terminated?
**Ans:** I would not decide based on connection age because a connection can exist for 24 hours due to connection pooling and still be perfectly healthy.
In PostgreSQL, I would distinguish session age from query age and state.
I would use `pg_stat_activity` to correlate each backend with its application name, client address, state, current query, query start time, transaction start time, and backend PID.
This tells me which microservice owns each connection and what that connection is doing.
If all the connections are genuinely executing queries, I would not randomly terminate any of them.
I would identify long-running or blocked queries, lock contention, and the microservice generating excessive concurrent work. I would correlate that with Prometheus application metrics and PostgreSQL metrics.
