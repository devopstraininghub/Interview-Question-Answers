## **Interview Questions and Answers**



**Q1. Please tell me how do you secure Jenkins?**

**A:** I secure CI/CD by applying least privilege, strong authentication, protected code and secret management, and controlled deployment access. For Jenkins, I integrate authentication with the organization's identity provider and ensure role-based access control. I give users only the permissions they need, such as separate administrator, developer and read-only access. I restrict access to Jenkins servers through private networking or an approved VPN. I store credentials in Jenkins Credential Manager or AWS Secrets Manager. I never store credentials inside Jenkinsfiles as source code.

**Q2. How would you retrieve credentials from Jenkins Credential Store in your Jenkins pipeline?**

**A:** I retrieve them through Jenkins Credential Binding mechanism, not by reading the credential store directly. I first create a credential in Jenkins with a unique ID, then reference that ID inside the pipeline using the `withCredentials` step.

**Q3. How do you implement manual approval gates?**

**A:** I generate an `input` step after the automated validation stages and before the production deployment stage. The pipeline pauses and waits for an authorized user to approve or reject the deployment.

**Q4. How do you create a parameterized build pipeline?**

**A:** I define parameters in the Jenkins pipeline so users can select values such as environments, image tags or deployment actions before starting the build. I validate those values and use them in later stages.

I can also create the same parameters through Jenkins job configuration using **This project is parameterized**. However, I prefer defining them in Jenkinsfiles because the configuration stays in version control. I restrict production choices with validation and avoid accepting shell commands or using credentials based on an unvalidated environment selection.

**Q5. What is a Shared Library in Jenkins?**

**A:** A Jenkins Shared Library is a version-controlled collection of reusable pipeline code. I use it to move common build, test, security, deployment, notification and approval logic out of individual Jenkinsfiles. This avoids duplicating pipeline code across repositories and provides consistency. I usually store the library in GitHub and configure it globally.

**Q6. How do you manage concurrent builds in Jenkins?**

**A:** I manage concurrent builds by deciding whether builds are independent or whether they modify the same shared resource. For independent builds, I allow concurrency and configure enough Jenkins agents or executors.

For deployments to shared environments or jobs using the same workspace, I prevent overlapping executions using the **Disable concurrent builds** option.

**Q7. What is Git cherry-pick?**

**A:** Git cherry-pick applies the changes from a specific commit onto my current branch without merging the entire source branch.

**Q8. How do you implement Git cherry-pick?**

**A:** I first switch to the target branch and update it from the remote repository. Then I cherry-pick the required commit using its commit ID.

For example, I fetch from origin, check out the release branch, pull the latest changes from the original release branch and cherry-pick the commit ID.

**Q9. What are Terraform modules?**

**A:** Terraform modules are reusable containers of Terraform resources. I use them to package related infrastructure such as VPC, EKS clusters, IAM roles or application load balancers into consistent and reusable units.

Every Terraform configuration has a root module, which contains the `.tf` files in the working directory.

**Q10. Have you created custom Terraform modules and made them centralized for others to use?**

**A:** Yes, I have created custom Terraform modules such as VPC, EKS clusters and IAM roles. I keep each module focused on one infrastructure responsibility and expose configuration through input variables and outputs.

**Q11. What is the purpose of using Terraform workspaces?**

**A:** Terraform workspaces allow us to use the same Terraform configuration with separate state files. I use them when multiple environments need to share the same infrastructure code but maintain independent states, such as development, staging and production.

Each workspace maintains a separate Terraform state, so a plan in development does not directly modify resources managed by staging or production.

**Q12. What are Terraform provisioners?**

**A:** Terraform provisioners execute scripts or commands on a local machine or remote resource during resource creation. I use them for tasks such as copying files to a server or running a cleanup command.

The main provisioners are:

- **Local-exec:** Runs a command on the machine where Terraform runs.
- **Remote-exec:** Runs commands on a remote resource.

I use provisioners only as a last resort because Terraform cannot fully model their actions and they can reduce repeatability. For server configuration, I prefer user data or immutable machine images. If I must use a provisioner, I make it idempotent, protect secrets and define connection timeouts and failure behaviour.

**Q13. What is the difference between count and for_each?**

**A:** Both `count` and `for_each` create multiple instances of a resource or module, but they are different.

I use `count` when I need a fixed number of nearly identical resources. For example, I can use `count = 3` to create three instances.

I use `for_each` when each instance needs a stable and meaningful key or different configuration.

The main difference is that `count` uses numeric indexes, while `for_each` uses stable keys. If I remove an item from the middle of a list using `count`, Terraform can shift indexes and recreate unrelated resources. With `for_each`, Terraform changes only the affected key.

**Q14. How do you troubleshoot an OOMKilled error in Kubernetes?**

**A:** I treat OOMKilled as a memory-limit issue first. Kubernetes terminates a container when it exceeds its configured memory limit, and the container usually shows exit code 137.

I check the pods using `kubectl get pods` and describe them using `kubectl describe pod`. In the describe output, I check the container state reason, exit code, restart count and events. I also check current usage.

Then I check whether the application has a memory leak, unexpected traffic increases, large requests, insufficient caching or incorrect runtime configuration. For Java applications, I verify heap settings such as `XMS` and `XMX`.

**Q15. What are taints and tolerations?**

**A:** A taint is applied to a Kubernetes node to prevent pods from being scheduled there unless they explicitly tolerate that taint. A toleration is configured on a pod to allow it to run on a node with a matching taint.

I use taints to reserve nodes for specific workloads, such as system components, production applications or dedicated teams.

The main taint effects are:

- NoSchedule
- PreferNoSchedule
- NoExecute

A toleration only allows a pod onto a tainted node; it does not force the pod to run there.

**Q16. What is the difference between a CNI plugin and kube-proxy?**

**A:** A CNI plugin provides networking for pods. It creates the pod network interface, assigns an IP address, configures routes and enables communication between pods, nodes and external networks.

In Amazon EKS, the default CNI is AWS VPC CNI. It assigns pod IP addresses from the VPC subnet through Elastic Network Interfaces.

I troubleshoot it by checking the AWS node DaemonSet, pod events, subnet IP availability, ENI limits and IAM permissions.

Kube-proxy handles Kubernetes service networking. It runs on each node and programs networking rules using IPVS or iptables, depending on the configuration.

**Q17. How do you create CRDs for Prometheus and Grafana?**

**A:** I create CRDs when I need Kubernetes to understand new resource types, such as ServiceMonitor and Prometheus or Grafana resources.

In practice, I install the Prometheus and Grafana operators because the operators provide the CRDs and controllers that manage those resources.

For example, I install the kube-prometheus-stack Helm chart, verify the CRDs and create custom resources supported by the operator. A ServiceMonitor tells Prometheus how to scrape an application.

**Q18. How do you create a Python code to connect using an SSH client?**

**A:** I use the Paramiko library to create an SSH client. I consider host key verification, authentication, connection timeouts and command execution. After execution, I perform proper cleanup.

I install the Paramiko library and import it in the script. I do not hardcode private keys or passwords in the script.

**Q19. How do you run a Linux command in Python?**

**A:** I use Python's `subprocess` module. I prefer `subprocess.run()` because it executes the command, waits for completion, captures the output and returns the exit status.

**Q20. How do you handle exceptions in Python?**

**A:** I handle exceptions using `try`, `except`, `else` and `finally` blocks. I catch specific exceptions, log useful content, clean up resources and return a clear failure status instead of hiding the problem.

**Q21. How do you parse a JSON file in Python?**

**A:** I use Python's built-in `json` module. I open the file with UTF encoding and load it into a Python dictionary or list. I validate the required fields and handle file and JSON parsing errors.

**Q22. What is the difference between a list and a tuple?**

**A:** A list is mutable, so I can add, remove or update elements after creation. A tuple is immutable, so its elements cannot be changed after creation.

**Q23. What monitoring tools have you worked with?**

**A:** I use Amazon CloudWatch, Prometheus, Grafana, New Relic and Fluent Bit and Fluentd for centralized logging.

I mostly use CloudWatch for AWS infrastructure and service monitoring.

**Q24. How do you collect traces?**

**A:** I collect traces by instrumenting the application with OpenTelemetry. The application creates a trace for each request and adds spans for important operations such as HTTP calls, database queries, message processing and external service calls.

Each trace carries a trace ID, and each operation has a span ID. I propagate the trace context through HTTP headers so I can follow one request across multiple microservices.

The application sends traces through OpenTelemetry Collectors. The collector receives the telemetry data, processes it, adds attributes and forwards the traces to backends such as AWS X-Ray, Grafana Tempo or New Relic.

**Q25. How do you integrate Prometheus with Grafana?**

**A:** I integrate them by considering Prometheus as a data source in Grafana. Prometheus collects and stores metrics, while Grafana queries Prometheus and displays those metrics in dashboards and alerts.

**Q26. What AWS services have you worked with?**

**A:** I have worked with EC2, VPC, S3, RDS, Route 53, IAM, load balancing, Auto Scaling, CloudWatch, Lambda and Secrets Manager.

**Q27. How does Route 53 work?**

**A:** Route 53 is a managed DNS service. It translates domain names, such as `example.com`, into IP addresses or AWS resource endpoints so clients can reach the application.

When a user requests a domain, the DNS resolver queries Route 53 hosted zones. Route 53 matches the record and returns the configured value, such as an Application Load Balancer DNS name, CloudFront distribution, EC2 address or another domain.

I use hosted zones and private hosted zones to resolve names only inside the associated VPCs.

**Q28. How do you optimize costs in AWS?**

**A:** I start by measuring the current spend using AWS Cost Explorer, budgets, cost allocation tags and cost reports. I group costs by account, environment, application and owner so I can identify the largest spend and unusual resources.

For compute, I right-size instances using CloudWatch CPU and memory metrics. I stop non-production instances outside working hours, use Auto Scaling and select instance types based on application requirements.

For stable workloads, I use Savings Plans or Reserved Instances. For interruptible batch workloads, I use Spot Instances.

For EKS, I right-size pod requests and limits, configure HPA and Cluster Autoscaler, remove unused nodes and use Spot capacity where suitable.

For storage, I use S3 lifecycle policies to move older objects to less expensive storage classes.

**Q29. How do you manage dependencies in Lambda functions?**

**A:** I manage Lambda dependencies by packaging them with the function using a Lambda layer or deploying the function as a container image.

For Python Lambda functions, I install dependencies into a directory and create a deployment package. I upload the Lambda ZIP through Terraform, AWS CLI or the CI/CD pipeline.

I pin dependency versions, run unit tests, scan dependencies for vulnerabilities and publish versioned artifacts.

For dependencies shared by multiple functions, I use Lambda layers.

**Q30. What is cross-region replication in S3?**

**A:** Cross-region replication means automatically copying data from one AWS region to another region. I use it for disaster recovery, business continuity, lower latency and protection against regional failures.

For Amazon S3, I enable versioning on both buckets, configure an S3 replication rule and grant the replication IAM role permissions to read from the source bucket and write to the destination bucket.
