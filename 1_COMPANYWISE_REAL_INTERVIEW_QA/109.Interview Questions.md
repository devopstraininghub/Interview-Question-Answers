**Q4. Can you explain the architecture of any product or project from your past experience? I need a complete AWS architecture.**

**Answer:** In my current project, I work on a microservices application hosted on AWS using Amazon EKS. I manage infrastructure, Kubernetes deployments, CI/CD pipelines, security, and monitoring.

I will explain the architecture from user requests to backend services.

First, I use Amazon VPC configured across multiple Availability Zones for high availability.

Within the VPC, I have public and private subnets. Public subnets contain the Application Load Balancer and NAT Gateways, while private subnets contain EKS worker nodes and application workloads.

I use Internet Gateways, NAT Gateways, security groups, and route tables to manage network connectivity securely.

For the application layer, I use Amazon EKS to host containerized microservices. When a user accesses the application, the request first goes through Route 53 for DNS resolution. Then the request reaches the Application Load Balancer, which forwards traffic to Kubernetes.

I deploy applications using Docker images, Kubernetes deployments, and Helm charts.

For databases, I use Amazon RDS for relational databases, including PostgreSQL and MySQL. I keep the database in a private subnet and restrict access through security groups.

I use Amazon S3 for application files, backups, and storage requirements.

For CI/CD, I use GitHub, Jenkins, Docker, Helm, and Argo CD.

When developers push code to GitHub, Jenkins triggers the pipeline. Jenkins performs code checkout, Maven builds the artifact, and we perform unit testing and security scanning using SonarQube.

After successful validation, Jenkins builds the Docker image and pushes it into the container repository.

Then I use Argo CD for GitOps-based deployment. Argo CD monitors the Git repository containing Kubernetes manifests and Helm configurations.

For infrastructure automation, I use Terraform to provision AWS infrastructure, including VPC, EKS clusters, IAM roles, security groups, and other supporting resources.

**Q5. Your database is hosted in a private subnet. If you need to connect to the database and run a query to address a customer issue, how do you connect?**

**Answer:** In my project, I prefer using AWS Systems Manager Session Manager to connect to the database.

First, I access an authorized EC2 instance in the private subnet using Session Manager. I ensure that the EC2 instance has the required IAM permissions and that its security groups allow communication with RDS.

Then I retrieve the database credentials from AWS Secrets Manager.

**Q6. If the engineering team wants database access, how do you provide access to them?**

**Answer:** I provide access through AWS IAM, Secrets Manager, Systems Manager Session Manager, and database-level permissions.

We follow the least-privilege principle. I verify the engineer's access request and obtain the required approval. Then I assign an IAM role with restricted Systems Manager permissions.

**Q7. If I request access to your database, which is in a private subnet, how do you provide access? How should I connect to the database, and how do you restrict my privileges?**

**Answer:** I use IAM and database-level permissions to manage access.

I use an administrative database account with an RDS database role to create users and manage roles. I use the appropriate administrative permissions and grant only the required privileges.

For read-only access, I grant SELECT permissions to the required tables.

I use an authorized database administration account with the required role to create and manage database users.

For read-only users, I grant CONNECT on the database, USAGE on the schema, and SELECT on the required tables.

AWS IAM controls access to AWS resources, while PostgreSQL roles control permissions inside the database.

**Q8. If I have access to the EC2 instance and you provide access to Secrets Manager, I can retrieve the database password and connect as a database user. How would you control my access?**

**Answer:** I would not provide unrestricted EC2 administrator access or unrestricted Secrets Manager access to engineers.

I configure the EC2 instance with a least-privilege IAM instance role.

Root access gives the user complete control over the EC2 operating system. However, Linux root privileges do not automatically provide AWS administrative permissions. The user can access only the AWS permissions available through the instance role or other credentials present on the instance.

I control PostgreSQL database access using roles and privileges. The IAM role does not automatically grant database access. I authenticate each database user separately. For example, I create a read-only database user and grant only the required permissions.

I also restrict access to the database using default privileges when required.

**Q14. Have you ever performed security patching on EC2 instances?**

**Answer:** Yes, I have experience with EC2 instances.

**Q15. How do you perform security patching on EC2 instances?**

**Answer:** Generally, I use AWS Systems Manager Patch Manager for automated security patching.

First, I verify that the EC2 instance has the SSM Agent installed, the required IAM role, and connectivity to Systems Manager.

Next, I configure a patch baseline to define which security patches AWS should approve for installation.

Before patching production instances, I create EBS snapshots or AMI backups and schedule a maintenance window.

Then I use SSM Patch Manager to scan for missing security patches and install approved updates.

I follow a controlled patching process using AWS Systems Manager Patch Manager instead of directly installing patches on production EC2 instances.

**Q16. Suppose an EC2 instance has a corrupted volume and you need to recover data from it. There is only one volume attached to the instance. How would you recover the data?**

**Answer:** First, I check whether the EBS volume itself is corrupted or only the file system is damaged.

Since the EC2 instance has only one volume, which is the root volume, I follow the recovery process.

First, I stop the affected EC2 instance to prevent further data corruption. I create an EBS snapshot of the corrupted volume.

Then I create a new EBS volume from that snapshot and attach it to a healthy recovery EC2 instance in the same Availability Zone as a secondary volume.

Once I attach it, I connect to the recovery instance and identify the data.

**Q17. If you take a snapshot of an already corrupted EBS volume, what is the use of it?**

**Answer:** A snapshot of an already corrupted EBS volume preserves the existing data, including the corruption. Creating a snapshot does not automatically repair the corrupted data.

I take the snapshot mainly to preserve the current state of the volume before attempting recovery. Then I create a new volume from the snapshot and attach it to a healthy EC2 instance.

**Q18. Suppose you have a 1 TB EBS volume, but you are using only 200 GB. You want to downsize the volume. What would you do?**

**Answer:** AWS EBS does not directly support reducing the size of an existing volume. EBS supports increasing volume size but not decreasing it.

I would migrate the data to a new, smaller EBS volume.

If the existing volume is 1 TB and only 200 GB is used, I would recommend creating a 300 GB or 400 GB EBS volume, allowing additional space for future growth.

**Q19. How would you migrate the data to the smaller volume?**

**Answer:** First, I create a new EBS volume in the same Availability Zone as the EC2 instance and attach it as a secondary disk.

I identify the disk usage, create a file system, and mount the new volume.

Then I use `rsync` to migrate the data while preserving permissions and ownership.

I verify the migrated data, update the mount configuration, and mount the new volume at the original location.

Finally, I restart the application, validate its functionality, and delete the old volume after successful verification and backup.

**Q20. If an S3 bucket contains critical data and you are asked to secure it, what steps would you take?**

**Answer:** First, I enable S3 Block Public Access at both the account and bucket levels.

Second, I apply least-privilege IAM policies and bucket policies.

Then I enable SSE-KMS encryption using AWS KMS customer-managed keys.

I enforce HTTPS using a bucket policy that denies insecure transport, protecting data during transmission.

I also enable S3 versioning and Object Lock.

I enable CloudTrail data events for S3 and configure S3 VPC endpoints to restrict bucket access to approved network paths where appropriate.

I also use Amazon Macie and AWS Config to identify sensitive data and continuously monitor security compliance.

This protects critical S3 data through strict access control, encryption, continuous monitoring, and reliable recovery mechanisms.

**Q21. Suppose one common service needs to connect to four other services running on four different instances. The connection should be private and should not use the internet. How would you plan for this?**

**Answer:** I would design this using AWS VPC private networking.

First, I would deploy all five EC2 instances in private subnets within the same VPC.

Then I would assign private IP addresses to each instance.

I would configure security groups so that the common service can communicate with the other four services only on their required application ports.

I would ensure the VPC route table supports communication through the local VPC route.

Then I would use Route 53 private hosted zones so the common service can connect using private DNS names instead of IP addresses.

I would also configure network ACLs to allow the required traffic and block unnecessary access.

I would enable TLS encryption between services to secure communication.

Finally, I would validate connectivity using `curl` and VPC Flow Logs.
