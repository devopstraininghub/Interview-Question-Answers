### 4. Can you explain the steps involved in a Kubernetes upgrade? Which plane would you upgrade first, followed by which components? What add-ons are involved, and what is the current Kubernetes version?

**Answer:**

In my current project, I work with EKS clusters and follow a proper upgrade sequence to minimize downtime.

First, I perform pre-upgrade checks, such as checking the current Kubernetes version, cluster health, node status, and running pods. I also review deprecated APIs and compatibility with the target Kubernetes version.

I use `kubectl version` to check the Kubernetes client and server versions and `kubectl get nodes` to verify worker node versions.

Secondly, I upgrade the control plane first. In AWS EKS, AWS manages the control plane, so I initiate the upgrade through the AWS Console or AWS CLI.

I upgrade one minor version at a time because EKS does not support skipping minor versions during control plane upgrades.

Thirdly, I upgrade the EKS add-ons, including VPC CNI, CoreDNS, kube-proxy, and the EBS CSI driver. I verify their compatibility with the target Kubernetes version and upgrade them in the required order.

Fourthly, I upgrade the worker nodes using EKS managed node groups and perform a rolling update. During this process, I ensure workloads move safely to healthy nodes. I also verify pod disruption budgets, resource availability, and application replicas to minimize downtime.

Finally, I perform post-upgrade validation by checking node readiness, pod status, application health, and Kubernetes events.

### 7. What strategies would you use to optimize the performance of a cluster running nearly 500+ services?

**Answer:**

For a Kubernetes cluster running 500+ services, I would focus on resource optimization, autoscaling, monitoring, networking, and workload distribution.

1. **Resource Optimization:** I would analyze CPU and memory utilization using Prometheus and Grafana. Based on actual usage, I would configure appropriate resource requests and limits to avoid resource wastage and prevent out-of-memory issues.

2. **Autoscaling:** I would implement HPA (Horizontal Pod Autoscaler) to scale application pods based on CPU, memory, or application metrics.

3. **Workload Distribution:** I would distribute workloads across multiple availability zones using topology spread constraints and pod anti-affinity rules. This helps prevent overloading individual nodes.

4. **Network Optimization:** With 500+ services, I would monitor CoreDNS performance, VPC CNI, IP address utilization, network latency, and service communication. I would also check for DNS bottlenecks and network connection issues.

5. **Monitoring and Alerting:** I would use Prometheus, Grafana, and CloudWatch to monitor node utilization, pod restarts, API server latency, network performance, and application response times.

6. **Application Optimization:** I would identify services consuming excessive CPU or memory and investigate them accordingly.

### 9. Can you explain how this Deployment works?

**Answer:**

In this YAML file, I define three replicas. Kubernetes ensures that three application pods are running.

When I apply this manifest using `kubectl apply -f`, the Deployment controller creates a ReplicaSet, and the ReplicaSet manages the three pods.

The selector and pod labels help the Deployment identify which pods belong to it. If a pod fails or gets deleted, the ReplicaSet automatically creates a replacement pod to maintain the desired replica count.

For application updates, I configured a rolling update strategy with `maxSurge: 1` and `maxUnavailable: 0`.

This means Kubernetes can create one additional pod during an update while maintaining the desired number of available replicas.

I have also configured readiness probes to determine when pods can receive traffic and liveness probes to restart unhealthy containers.

For rollout, I use `kubectl rollout status deployment` to monitor deployment progress.

Basically, this Deployment handles pod creation, scaling, self-healing, and application updates.

### 10. Why have you written maxSurge under the rolling update strategy?

**Answer:**

`maxSurge` defines the maximum number of additional pods Kubernetes can create above the desired replica count during a rolling update.

### 16. What is the difference between a Security Group and a Network ACL?

**Answer:**

In AWS, I use Security Groups and Network ACLs to control network traffic within a VPC.

A Security Group operates at the instance or network interface level, whereas a Network ACL operates at the subnet level.

The main difference is that Security Groups are stateful, so return traffic is automatically allowed.

Network ACLs are stateless, so I need to configure both inbound and outbound rules.

### 17. Can a Security Group be associated with multiple instances?

**Answer:**

Yes, we can associate a single Security Group with multiple EC2 instances within the same VPC.

For example, I can attach one Security Group to five EC2 instances to apply the same inbound and outbound traffic rules.

Also, one EC2 instance can have multiple Security Groups associated with its network interface.

### 18. What happens if you don't define any inbound rules in a Security Group?

**Answer:**

If I don't define any inbound rules, the Security Group blocks all incoming traffic by default.

Because Security Groups are stateful, they still allow response traffic for connections initiated from the instance, provided the outbound rules permit those connections.

### 19. What is the difference between an IAM Role and an IAM Policy?

**Answer:**

An IAM Role is an identity that AWS services or authorized users can assume to access AWS resources.

An IAM Policy is a JSON document that defines permissions, specifying which actions are allowed or denied on particular resources.

### 20. How do you secure your S3 buckets?

**Answer:**

I secure S3 buckets by following least privilege access, encryption, and monitoring best practices.

1. I enable S3 Block Public Access to prevent accidental public exposure.
2. I configure IAM policies and bucket policies to allow only authorized users and services to access the bucket.
3. I enable server-side encryption using SSE-KMS to protect data at rest.
4. I enforce HTTPS connections through bucket policies to protect data in transit.
