### Q3. Some pods in your EKS cluster are stuck in Pending state, but the worker nodes are Ready. How would you troubleshoot this? Which commands would you run?

**A:** I would start by checking the pod events because the scheduler usually explains the reasons.

I would use `kubectl get pods` to get the pod details and `kubectl describe pod` with the specific namespace to inspect the events.

I would also use `kubectl get events` with the namespace and sort the events by timestamp.

I would look for issues such as CPU or memory constraints, taints, affinity conflicts, node selectors, and volume binding problems.

A node can show Ready while still having insufficient allocatable CPU or memory for a particular pod. I would compare the pod's resource requests with the node's available resources.

### Q4. Kubernetes reports "0 out of 5 nodes are available: 5 Insufficient CPU", but CPU utilization on the nodes is only 30%. Why is Kubernetes saying insufficient CPU?

**A:** Kubernetes schedules pods based on their requested CPU, not on the current CPU usage shown by the operating system or monitoring tools.

For example, a node may have four CPUs and currently use only 30%, but existing pods may already have most of the node's allocatable CPU reserved through their resource requests.

If a pending pod requests more CPU than the remaining allocatable capacity, the scheduler reports insufficient CPU.

I would verify this using `kubectl describe node` and compare the node's capacity, allocatable resources, and allocated resources.

### Q5. Pods are stuck in ContainerCreating with the error "Failed to create pod sandbox: failed to assign an IP address to container". How would you troubleshoot this in AWS EKS?

**A:** I would treat this as an EKS networking or VPC issue rather than a CPU or memory issue.

AWS VPC assigns ENI IP addresses to pods. I would first check the CNI components and available IP capacity.

I would start with pod events using `kubectl describe pod` and look for errors related to IP allocation, ENI attachment, subnet exhaustion, EC2 API calls, or IAM permissions.

On the AWS side, I would check the available IP addresses in the node's subnet.

### Q6. Someone manually modifies a security group through the AWS console after Terraform has provisioned the infrastructure. How would you identify this drift and resolve it without affecting other resources?

**A:** I would first avoid applying anything directly. I would confirm the current Terraform workspace, backend, variables, and AWS account being used.

I would run `terraform init`, `terraform workspace show`, and `terraform plan`.

Terraform plan compares the configuration and state with the actual AWS infrastructure and shows manual changes. Terraform refreshes the state during planning unless refresh is disabled.

I would inspect the specific resource using Terraform state commands and review the security group directly in AWS to confirm the actual rules. I would also identify who made the changes using CloudTrail.

After identifying the difference, I would decide which configuration is the source of truth.

If the manual change is required, I would update the Terraform code, run formatting and validation, and review the plan again.

If the manual change is not approved, I would keep the Terraform configuration unchanged and apply only the reviewed plan so Terraform removes the unwanted rules.

### Q8. Explain the Python health-check script shared with you step by step. What critical bugs or risks do you see, and what improvements would you make?

**A:** The script imports `requests` to send HTTP requests and `time` to pause between retries.

It defines a list of application health URLs and checks each URL through a health-check function.

The function attempts each URL three times using a loop. For every attempt, it sends a GET request. If the response status code is 200, it prints that the URL is healthy and returns `True`.

If the response has another status code, it prints the status after each failed attempt. It waits for two seconds between attempts. If all three attempts fail, it returns `False`.

The main function loops through all the URLs and calls the health-check function for each one.

I identified several issues:

1. The script prints that all applications are healthy even when one or more health checks fail because it ignores the Boolean results returned by the health-check function.
2. The `requests.get()` call has no timeout. If an endpoint does not respond, the script can wait indefinitely. I would add connection and read timeouts.
3. It treats only HTTP 200 as healthy. Other successful status codes, such as 204, may also be valid depending on the application. I would define the expected status codes clearly.
4. It does not validate the response body. An endpoint may return HTTP 200 even when the application itself reports an unhealthy status.
5. It catches only limited exceptions. I would handle request exceptions and unexpected results carefully.

### Q9. You are using an Ansible playbook to deploy an application across 20 servers. You want to deploy five servers at a time, but if deployment fails on any server in a batch, you want to stop the deployment. How would you design this in your playbook?

**A:** I would use `serial: 5` to process the hosts in batches of five.

I would also use `any_errors_fatal: true` so that a failure on any host stops the entire play and prevents Ansible from moving to the next batch.

`serial: 5` controls the batch size. Ansible deploys to five servers, waits for the tasks to finish, and then starts the next batch.

`any_errors_fatal: true` makes a failure on any host stop the play.

I would also make sure that deployment and health-check tasks fail properly by avoiding ignored errors. I would use blocks and rescue if I needed cleanup or rollback after a failed batch.

### Q10. Jenkins successfully builds a Docker image and pushes it to ECR. Argo CD shows the application as Synced and Healthy, but users are still accessing the old application version. How would you troubleshoot this?

**A:** I would first confirm whether the new image was actually deployed and whether users are reaching the expected environment.

Argo CD showing Synced and Healthy confirms that the live Kubernetes resources match Git and that the health checks pass. It does not always prove that users are receiving the new application version.

I would check the deployed image on the running pods using commands such as `kubectl get pods`, `kubectl get deployments`, and `kubectl describe pod`. I would compare the image with the one pushed to ECR.

A common cause is reusing the same image tag, such as `latest` or `dev`. If the Git manifest still contains the same tag, Argo CD may not detect a manifest change or trigger a new rollout.

I prefer immutable image tags based on the Git commit SHA or release number.

I would also:

- Check the rollout status and replica status.
- Verify that all replicas are using the new image.
- Confirm that old pods are no longer serving traffic.
- Inspect the Service and endpoint routing.
- Confirm that the Service selector matches the intended pods.
- Check the Ingress or AWS Load Balancer configuration.
- If blue-green or canary deployment is used, verify that traffic routing and target groups point to the new version.

A new pod can be healthy while traffic is still directed to the old service.

### Q11. An application running on EKS suddenly experiences high response times, but CPU and memory usage are normal and no pods are restarting. How would you investigate this using Prometheus and Grafana? Which metrics would you check?

**A:** I would first confirm the scope, start time, affected endpoints, and whether the latency affects all users or only a specific route.

Normal CPU and memory usage do not rule out problems with dependencies, networking, connection pools, or application code.

In Grafana, I would check:

- Application latency.
- Error rate.
- P50, P95, and P99 latency.
- Latency by endpoint, method, and status code.
- Request rate.
- Active requests and in-flight requests.

If the application exposes Prometheus metrics, I would use PromQL queries to check HTTP request duration and request rates.

I would also check whether the latency starts at the application level or before it, such as at the Kubernetes Ingress.

I would review pod-level networking and container metrics and compare latency across pods to identify whether one pod, node, or availability zone is affected.

I would check pod readiness, node health, and network errors.

Even when CPU usage looks normal, thread execution or connection pool saturation can cause latency.

Next, I would investigate dependencies, including database metrics such as connection count, connection wait time, slow queries, and query latency. I would also check external API latency.
