### Q10. If you deploy a Kubernetes pod without specifying resource limits, what default resources will be allocated to it?
**A:** By default, Kubernetes does not automatically assign CPU or memory requests or limits unless the namespace has a LimitRange configured.

If no LimitRange exists, the pod has no resource requests and no resource limits. The scheduler does not reserve guaranteed CPU or memory for it.

The container can consume available node resources until the node experiences resource pressure. During memory pressure, Kubernetes can evict the pod or an OOM kill can occur.

If the namespace has a LimitRange, Kubernetes applies the default requests and limits to containers that do not specify them.

Requests help the scheduler place the pod, while limits cap its resource usage. I can also use ResourceQuota at the namespace level to control total consumption and prevent one team or workload from exhausting cluster resources.

### Q11. What are the different types of Kubernetes Quality of Service (QoS) classes?
**A:** There are three QoS classes: Guaranteed, Burstable, and BestEffort.

### Q12. What is the BestEffort QoS class?
**A:** BestEffort is the lowest Kubernetes Quality of Service class. A pod receives this class when its containers do not have CPU or memory requests or limits specified.

### Q13. What does it mean when BestEffort pods have the lowest priority and are the first candidates for eviction? When would they be evicted?
**A:** BestEffort pods can be evicted when the node cannot safely continue running all workloads.

The most common situation is memory pressure. For example, a workload may consume memory, and the Kubernetes kubelet detects that available memory has fallen below the threshold. Kubernetes then starts reclaiming resources.

Kubernetes can also evict pods when the node experiences disk pressure, inode exhaustion, or other configured eviction conditions.

The kubelet first tries to reclaim resources such as unused images and container logs. If that is not enough, it evicts pods according to their QoS class and resource usage. BestEffort pods generally become eviction candidates before Burstable and Guaranteed pods.

### Q14. What kind of workloads should be scheduled with the BestEffort QoS class?
**A:** I use BestEffort pods only for non-critical workloads that can tolerate eviction.

Examples include temporary development pods, debugging tools, disposable test workloads, and low-priority batch jobs that do not store important data.

I do not use BestEffort for customer-facing APIs, payment services, databases, message brokers, or monitoring components. Those workloads need predictable resources and defined CPU and memory requests and limits.

### Q15. Do you know about taints and tolerations? Which technology are they part of?
**A:** Yes. They are part of Kubernetes scheduling features. They control which pods can run on which nodes.

### Q16. If a node has a taint and you want a pod to be scheduled only on that particular node, what would you do?
**A:** I need to configure both sides. I apply a taint to the node and add a matching toleration to the pod.

Since toleration only permits scheduling, I also add a node label and use a node selector or node affinity to force the pod onto that particular node or node group.

### Q19. What is the significance of HTTP error 429?
**A:** HTTP 429 means "Too Many Requests." The client has sent more requests than the server or API allows within a defined time window. It indicates rate limiting and is not usually an application failure.

### Q20. Why do you configure rate limiting?
**A:** We configure rate limiting to protect APIs and their dependent services from excessive traffic.

It prevents one client, user, or service from consuming all available CPU, memory, database connections, or network capacity.

Rate limiting helps maintain availability, provide fair usage, control costs, protect against abuse, and safeguard downstream systems.

### Q21. Can rate limiting be used as a security feature in an API?
**A:** Yes, rate limiting can be used as a security control.

### Q22. What types of cyberattacks can rate limiting help protect against?
**A:** Rate limiting can control how many requests a client IP address, user, or token can send during a defined time window.

It protects the API from resource exhaustion and automated abuse. It can help protect against brute-force attacks, credential stuffing, HTTP flood attacks, and automated API abuse.
