### 3. What would be your strategy for deploying this product for customers?
**Answer:** I would use a repeatable, secure, and automated deployment strategy. First, I would understand the customer's environment and requirements. Then I would provision the required infrastructure using Terraform, deploy the containerized application on Kubernetes, and automate releases through CI/CD.
### 4. How would you handle security?
**Answer:** I would follow the principle of least privilege and secure secrets management. I would control AWS access through IAM roles and Kubernetes access through RBAC. I would store credentials in AWS Secrets Manager instead of keeping them in code.
### 5. How would you handle security for an on-premises deployment?
**Answer:** I would follow the same core security principles. I would use Kubernetes RBAC for access control and Kubernetes Secrets or the customer's approved secret management solution for credentials. For code quality and security scanning, I would use SonarQube and Trivy to find vulnerabilities in Docker images.
### 6. Is Trivy good enough?
**Answer:** In my experience, Trivy is effective for scanning Docker images for known vulnerabilities and integrating those checks into CI/CD pipelines. I have used it along with SonarQube to prevent builds from progressing towards production. I would treat Trivy as one security layer, not the complete security solution. I would combine it with access controls, secrets management, and monitoring for overall security.
### 7. NGINX is deprecated. What would be its replacement?
**Answer:** For Kubernetes on AWS EKS, I would commonly use the AWS Load Balancer Controller with ALB. The exact replacement depends on the environment and routing requirements.
For on-premises deployments, I would use a supported ingress solution such as Traefik or HAProxy.
