**Q9. What is the difference between canary deployment and blue-green deployment?**

**A:** In canary deployment, we have two versions. We initially test the latest version internally. For example, if we have 10 instances, we first test the deployment on two instances. If everything works well, we gradually increase the number of instances.

**Q10. Can you explain the process of deploying an application to Amazon EKS?**

**A:** We use a Jenkins pipeline. When a developer pushes code, a webhook triggers the Jenkins pipeline.

First, Jenkins checks out the code and builds the application. Then it performs code analysis using SonarQube. After that, we build the Docker image and push it to Amazon ECR.

Finally, we deploy the application to EKS using Helm charts.

**Q16. If a deployment is successful but the application pods keep restarting, how do you troubleshoot the issue?**

**A:** First, I check the EKS dashboard. Then I use the following commands:

- `kubectl get pods -n <namespace>`
- `kubectl describe pod <pod-name> -n <namespace>`
- `kubectl logs <pod-name> -n <namespace>`
- `kubectl logs <pod-name> -n <namespace> --previous`
- `kubectl get events -n <namespace>`

If the pod has already crashed, I check the previous container logs using the `--previous` option.

**Q17. What information do you get from `kubectl describe pod` when a pod restarts?**

**A:** It shows the current state, restart count, and recent events. It may show issues such as resource limits, OOMKilled, failed liveness probes, missing configuration, and image errors.

**Q18. How would you troubleshoot a CrashLoopBackOff issue?**

**A:** First, I check the pod details using `kubectl describe pod` with the namespace. Then I check the previous logs using `kubectl logs --previous`.

I verify the container commands, image, environment variables, and secrets. If the pod is OOMKilled, I review memory usage and adjust the resources through an approved change.

After fixing the issue, I redeploy or roll back to the previous version.

**Q19. Have you implemented HPA (Horizontal Pod Autoscaler)?**

**A:** Yes. I have worked on Horizontal Pod Autoscaler. It adjusts the number of pod replicas based on metrics. I also configured resource requests and limits.

**Q20. What minimum and maximum replica counts did you configure for HPA?**

**A:** The minimum was 10 replicas, and the maximum was around 30.

**Q21. Why did you configure a minimum of 10 replicas?**

**A:** We started with 10 replicas. If there was no load or alert, we discussed reducing the number to five in the next sprint.

**Q22. What is the difference between HPA and Cluster Autoscaler?**

**A:** HPA increases the number of application replicas based on CPU, memory, or custom metrics.

Cluster Autoscaler adds nodes when pods remain pending because existing nodes do not have enough capacity. It also removes underutilized nodes when they are no longer needed.

**Q23. What would you do if an ECS deployment fails?**

**A:** First, I check the ECS service events and deployment status using the AWS CLI command:

`aws ecs describe-services --cluster <cluster-name> --services <service-name>`

I verify the task definition, container image, ECR permissions, task execution role, CPU, and memory settings.

**Q24. Have you worked in SRE? What are your responsibilities?**

**A:** My SRE responsibilities include working with CloudWatch, Prometheus, and Grafana, responding to alerts, troubleshooting Kubernetes and AWS issues, supporting releases, and participating in 24/7 incident support.

**Q25. Can you explain one critical incident (P1) you handled and your approach?**

**A:** When a P1 incident occurs, I first confirm the customer impact and acknowledge the alert in the incident channel.

I check CloudWatch, Prometheus, and Grafana to identify when the issue started and which services are affected. Then I check recent deployments, Kubernetes pod health, application logs, events, and load balancer health checks.

If the issue is related to a recent release, I follow the rollback process. If it is related to capacity, I scale the workload or infrastructure after confirming the metrics.

**Q26. Who communicates with the client during critical incidents?**

**A:** It depends. If the team lead is available, the team lead initiates the communication. Otherwise, it depends on the situation and the person handling the incident.

**Q27. If you are on call and a critical incident occurs, how would you handle it?**

**A:** First, I acknowledge the alert and confirm the customer impact. Then I check the affected services and severity.

I investigate using CloudWatch, Prometheus, Grafana, Kubernetes events, application logs, and deployment history to isolate the failing layer.

After that, I take the safest recovery action, such as rolling back, scaling the workload, or restoring a failed dependency. I keep the incident channel updated and escalate to the team lead, Incident Manager, or application owner according to the runbook.

**Q28. Do you have runbooks for handling incidents?**

**A:** Yes, we follow runbooks.

**Q29. Do you have any SLAs or SLOs as part of your SRE responsibilities?**

**A:** SLA is the actual measurement, such as availability, request latency, error rate, or successful deployment rate.

SLO is the internal reliability target for availability or latency. An external commitment is made to the client, including the agreed service and possible impact if it is missed.

During incidents, I use metrics to understand customer impact and prioritize recovery.

**Q30. What is the difference between ELB and ALB?**

**A:** Application Load Balancer works at Layer 7, which is the application layer. Network Load Balancer works at Layer 4, which is the transport layer.

ALB uses HTTP and HTTPS protocols and supports path-based routing. NLB uses TCP or UDP and is suitable for low-latency applications.
